# msk_transport_hackathon_2026

- **transceiver** принимает пакеты NDTP от трекеров и публикует их в Kafka.
- **inference** читает пакеты из Kafka, считает прогноз и пишет пакет с прогнозом в PostgreSQL.
- **Grafana** показывает дашборд по данным из PostgreSQL.

## Запуск

```bash
docker compose up --build -d
curl -s -X POST http://localhost:18080/api/config -H 'Content-Type: application/json' -d @emulator_config.json
```

Вторая команда отдаёт конфиг эмулятору

| Порт | |
|---|---|
| `3000` | Grafana, логин для правок `admin` / `admin` |
| `8000` / `8001` | API transceiver / inference, Swagger на `/docs` |
| `9000` | NDTP, сюда подключается эмулятор |
| `5433` / `9094` | PostgreSQL / Kafka для хоста |

## Структура

```
services/transceiver/  NDTP → Kafka: server.py, ndtp.py, publisher.py
services/inference/    Kafka → модель → БД: consumer.py, features.py, delay.py, schedule.py, model.py, storage.py
models/                модель, расписание и список ТС для inference
db/init.sql            схема БД
grafana/               источник данных и дашборд
```

## Настройки окружения

| Переменная | По умолчанию | |
|---|---|---|
| `TRANSCEIVER_NDTP_HOST` | `localhost` | в compose `0.0.0.0` |
| `TRANSCEIVER_NDTP_SEND_ACK` | `true` | отвечать трекеру `NPH_RESULT`, когда Kafka приняла пакет |
| `*_KAFKA_BOOTSTRAP_SERVERS` | `localhost:9094` | в compose `kafka:9092` |
| `INFERENCE_DATABASE_URL` | `postgresql://transport:transport@localhost:5433/transport` | |
| `INFERENCE_MODEL_PATH` | не задан | в compose `/app/models/v1`; без него заглушка с прогнозом 0 |
| `INFERENCE_SCHEDULE_PATH`, `INFERENCE_UNITS_PATH` | не заданы | расписание и `unit_id` → `tr_id`; без них нет целевых остановок |
| `INFERENCE_PREDICT_EVERY_S` | `15` | прогноз по одному ТС не чаще раза в столько секунд |

`*` — префикс `TRANSCEIVER_` или `INFERENCE_`. Остальное — в `config.py` сервисов.

## API

| | | |
|---|---|---|
| transceiver | `GET /units`, `/units/{unit_id}` | последний пакет по трекерам |
| inference | `GET /health` | 503, если чтение из Kafka остановилось; сразу после этого сервис завершается |
| inference | `GET /predict/{unit_id}` | прогноз на момент последнего пакета, или 404 с причиной |
| inference | `GET /features/{unit_id}` | вход модели на тот же момент, или 404 с причиной |

## Расписание

`models/schedule.csv` — копия `dataset/validate/schedule_plan.csv`: только план, без факта. Если расписание в датасете поменяется, его нужно заменить и здесь. Подойдёт файл с колонками `tt_action_item_id`, `tr_id`, `time_begin`, `order_date`, `geom`, но только с планом на один `order_date`: время остановок считается от своего `order_date`, и план за несколько дней склеится в один суточный шаблон, где каждая остановка повторится по разу на день. Расписание повторяется каждый день: сутки начинаются за 15 минут до самой ранней остановки, поэтому наряды после полуночи относятся к предыдущему дню.

`models/units.csv` — пары `unit_id` → `tr_id` из `traffic.csv` датасета. В пакете NDTP есть только `unit_id`, а расписание привязано к `tr_id`.

## Модель

`models/v1` — веса `DelayPredictorGRU` из ноутбука обучения, сохранённые `torch.save(model.state_dict(), path)`. Модель прогнозирует задержку в секундах на целевой остановке: первой, чьё плановое время попадает в интервал от 10 до 15 минут после момента прогноза. Вход — 60 шагов по 7 признакам в порядке `FEATURES` из `features.py`, без нормализации.

Новая версия кладётся в `models/` под другим именем, в `INFERENCE_MODEL_PATH` указывается путь к ней, после чего inference перезапускается. Размеры сети (скрытый слой, число слоёв GRU) берутся из весов, число признаков должно остаться 7. Имя файла пишется в `model_version` прогноза.

Прогноз строится по пакету ТС, если у ТС есть `tr_id` в `units.csv`, целевая остановка по расписанию и хотя бы 60 точек за последние 20 минут. Телеметрия пишется в БД всегда, прогноз — только когда он построен.

Поэтому в `emulator_config.json` стоят `unit_id` реальных автобусов с самым полным расписанием: 1012706, 893159 и 1099984 (`tr_id` 132430, 122048, 133957). В перерывах по расписанию прогноза нет. Координаты эмулятор генерирует случайно, поэтому автобус не проезжает остановки, и `cur_dev_s` равен оценке снизу `T − план`: прогнозы показывают работу сервиса, а не реальные задержки.

Пакеты идут раз в 15 секунд (`intervalMs`). Так 60 точек занимают около 15 минут из 20-минутного окна, а каждый сосед попадает в 15-секундное окно один раз. При пакетах чаще раза в 15 секунд история сжимается до секунд, а соседи считаются по несколько раз. Первый прогноз появляется через 15 минут после старта. Можно искуственно уменьшить, чтобы снизить время прогноза.

## Как устроено

- **NDTP**: ячейки `Nav00`, `IntSensor02`, `Usi08`, `Can10`, `Lls15`, `Termo16`. Новый тип добавляется записью в `CELLS` в `ndtp.py`. На неизвестной ячейке остаток пакета пропускается. `NPH_RESULT` уходит только после того, как Kafka приняла пакет: если не приняла, ответа нет, и трекер считает пакет недоставленным.
- **Признаки** (`features.py`) повторяют `extract_rnn_sequences` из ноутбука обучения: 60 последних точек за 20 минут, расстояние до целевой остановки, соседи в 15-секундных окнах. Точки всех трекеров хранятся в памяти 2 часа 10 минут и после перезапуска inference копятся заново. Точка, время которой опережает время приёма пакета больше чем на минуту, отбрасывается: иначе точки всех остальных ТС оказались бы старше окна хранения.
- **`cur_dev_s`** (`delay.py`): организаторы берут задержку на последней остановке с планом ≤ T по факту прибытия, которого у опаздывающего автобуса к T ещё нет. Поэтому проезд остановки определяется по треку: ближайшая точка не дальше 60 м, после которой автобус уехал. Если автобус до этой остановки ещё не доехал, берётся оценка снизу `T − план`, но только когда она не старше 15 минут. Иначе это, скорее всего, перерыв на конечной.
- **Kafka**: топик `telemetry`, ключ `unit_id`, так что пакеты одного трекера идут по порядку. Данные не сохраняются между `down` и `up`. Сообщение, обработка которого упала с ошибкой, пишется в лог и пропускается. Если остановилось само чтение Kafka, inference пишет причину в лог и завершается, а Docker запускает его заново: контейнер со статусом unhealthy `restart: unless-stopped` не перезапускает.
- **БД**: ключ `(unit_id, received_at)`, потому что `request_id` эмулятор сбрасывает при каждой загрузке конфига. Если БД недоступна, inference ждёт, а сообщения копятся в Kafka. `db/init.sql` применяется только к новому тому, после изменений нужен `docker compose down -v`, это удалит данные. В `predictions` кроме прогноза (`score`, секунды) хранятся целевая остановка, её плановое время и `cur_dev_s`. Если том создан раньше, колонки можно добавить без потери данных:

  ```bash
  docker compose exec postgres psql -U transport -c "ALTER TABLE predictions ADD COLUMN IF NOT EXISTS target_stop_id bigint, ADD COLUMN IF NOT EXISTS target_planned_at timestamptz, ADD COLUMN IF NOT EXISTS cur_dev_s double precision"
  ```
- **Grafana**: образ `grafana-enterprise`, бесплатный и без AGPL. В БД ходит пользователь с правами только на чтение. Правки из интерфейса нужно экспортировать в `grafana/dashboards/transport.json`.
